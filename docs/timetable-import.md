# 時刻表更新流程

臺鐵改點時，遊戲資料不需要手動編輯 JSON，只要把新的時刻表檔案放進一個
資料夾再跑一個指令。本文說明流程、資料可信度，以及少數需要人工維護的部分。

目前資料為 **115 年 7 月 1 日（2026-07-01）實施**的時刻表。

---

## 更新步驟

1. 從臺鐵取得該次改點的 `.ods` 時刻表，全部放在同一個資料夾。
2. 執行匯入：

```bash
python -m railway_sim.dataset --source <時刻表資料夾>
```

3. 匯入程式會重新產生 `data/stations.json`、`data/routes.json`、
   `data/timetables.json`，並立刻用遊戲本身的載入器驗證一次。

先看結果不寫檔：

```bash
python -m railway_sim.dataset --source <時刻表資料夾> --dry-run
```

列出被略過的班次與原因：

```bash
python -m railway_sim.dataset --source <時刻表資料夾> --show-skipped
```

### 遇到不認得的站名

若來源出現對照表沒有的站名，匯入會**中止**並列出站名。這是刻意的：與其
悄悄漏掉一個車站，不如要求先確認。請在
[`data/station_registry.json`](../data/station_registry.json) 加一筆：

```json
{ "name_zh_tw": "新站名", "id": "XINZHANMING", "name_en": null, "name_en_status": "derived" }
```

`id` 只是本專案內部的識別碼，不是臺鐵的官方車站代碼。

## 資料從哪裡來

| 資料 | 來源 | 標記 |
|---|---|---|
| 站名、站序 | 臺鐵公布的時刻表 | `official` |
| 車次、車種、停靠站、通過站、時刻 | 同上 | `official` |
| 車站的車種停靠規則（`stop_rules`） | 由時刻表中實際辦客的班次統計 | 推導結果 |
| 區間長度（`length_m`） | 由排點時間推估 | `estimated_from_timetable` |
| 車輛型式（`rolling_stock_id`） | 由車種名稱與線別電氣化與否分派 | 推導結果（見下節） |
| 區間速限、月台、股道 | 無公開來源 | 測試值或 `null` |

車輛本身的性能不在匯入範圍內：`trains.json` 不受匯入改動，改點時不會被覆寫。

每個產生的檔案都帶有 `meta.provenance`，記錄實施日期、產生時間，以及每個
來源檔案的 SHA-256，因此隨時可以確認「現在用的是哪一次改點的資料」。

> **區間長度不是實際里程。** 時刻表沒有里程資料，因此以「該區間最短運轉
> 時間 × 標稱速度」推估，只為了讓運轉在比例上合理。實際里程另有公開來源
> 時應改用實際值（規格 §27）。

## 兩種表格排版

臺鐵的時刻表有兩種排版，同一個檔案裡可能兩種都有，一張工作表也可能含多個
表格區塊（例如「彰化→新竹」先山線、後海線；集集線順行與逆行左右並排）。

**排版 A（區間車）**：車站是欄、班次是列，站名縱書拆在連續兩到三個表頭列。

**排版 B（對號列車）**：班次是欄、車站是列。

### 竹南至彰化的並排欄位

排版 B 在竹南與彰化之間**把海線與山線的站名並排成左右兩欄**，兩欄共用同一
個時刻欄：

```text
 竹 南                     08:38   07:54
 後 龍        苗 栗        08:49   08:07     ← 左欄海線、右欄山線
 彰 化                     09:43   09:17
              ↑山線站名
```

究竟是哪一站，由該班次表頭的「山」／「海」標記決定。匯入時先由區間車時刻表
建立路網（因此知道苗栗屬山線、後龍屬海線），再依標記挑出正確的站名。

不處理的話，山線列車的時刻會被記到海線車站上，整條路徑也會跟著錯。

## 路線是怎麼算出來的

時刻表只給停靠站與時刻，沒有實際行經路徑，因此：

1. 由**區間車**時刻表的站序建立相鄰關係（區間車會列出區間內每一站）。
2. 刪掉「中間其實還有車站」的假相鄰——對號列車時刻表只列主要車站，
   直接相鄰不代表實際相鄰。
3. 併入 [`data/topology_overrides.json`](../data/topology_overrides.json)
   的分歧節點與成追線。
4. 每個班次以**印有時刻的停靠站**為路標逐段尋路；「山」「海」「追」標記
   用來在平行路線之間做選擇。

尋路時會套用分歧的轉向限制，因此不會走出「追分→分歧→彰化」這種實際上
不存在的捷徑（見下節）。

## 車輛型式是怎麼決定的

時刻表只有**車種**欄，沒有車輛型式。`dataset.build.rolling_stock_for()` 依兩件事
分派車輛型式：

1. **時刻表印出的車種名稱**（`ROLLING_STOCK_BY_CLASS`）。「自強號」是車種不是
   車輛型式：車種欄把 EMU3000 印成「自強3000」、普悠瑪與太魯閣各自成一欄，其餘
   印「自強」，四者是完全不同的車輛，不能一律當成 EMU3000。
2. **是否行經非電氣化支線**（`NON_ELECTRIFIED_BRANCH_STATIONS`）。只要**完整
   行經路徑**（尋路算出的每一個節點，不是只看時刻表印出時刻的停靠站）碰到集集線、
   內灣線（竹中至內灣）、平溪線或深澳線本身的任何一站，就是 DR1000 型柴油客
   車——即使該班次有一大段行程跑在電氣化幹線上（例如彰化直通車埕的集集線區間
   快）。用完整路徑而非只看時刻表站是刻意的：對號列車時刻表只印主要車站，實際
   尋路可能補入時刻表沒印出來的中間站，這些站一樣是列車真的會經過的地方。

清單只列**支線本身**的車站：二水、三貂嶺、瑞芳都在幹線上，停靠它們的幹線列車
不受影響。六家線（竹中至六家）已電氣化，新竹至六家的區間車維持 EMU900。

另有極少數車次由 `ROLLING_STOCK_OVERRIDE_BY_TRAIN_NUMBER` 逐車次覆寫，優先於
上述兩條規則——例如車次 209、221、238、246（自強號，東部幹線）由 DR3100 型柴聯
車擔當，時刻表的車種欄無法分辨這點，只能人工確認後逐車次覆寫。

改點時這幾份對照表通常不必動，只有臺鐵調整車輛運用或支線電氣化時才要維護。

> **完整路徑判斷會放大路網本身的錯誤，務必先確認路網是對的。**
> 曾發生過路網缺一條邊（瑞芳與四腳亭這兩個宜蘭線本線相鄰站沒有直接連線，
> 唯一連通路徑被迫繞經深澳線分歧），導致 157 個東部幹線班次的完整路徑「經過」
> 深澳線車站。正確修法是在下一節的 `add_station_links` 補上缺的那條邊，
> 而不是把這些班次的車輛型式改成 DR1000 將錯就錯——它們真的是電聯車。
> 改用完整路徑後，若看到某類車次大量被判成非預期的車輛型式，先懷疑路網
> 是不是缺邊或多繞了路，不要急著加車輛型式的例外。

## 需要人工維護的部分

[`data/topology_overrides.json`](../data/topology_overrides.json) 存放時刻表
表達不出來、但運轉規則必需的知識。**改點時通常不需要動它**，只有實體路網或
線別歸屬改變時才要維護：

- **分歧節點與倒插方向限制**：成追線由成功站南方的分歧朝成功方向倒插接入
  山線，因此追分方向的列車進入該分歧後只能往成功，不能直接轉向彰化
  （規格 §10、chat.md v1.5-14）。
- **線別歸屬**：哪一段屬山線、海線、縱貫線。
- **共用咽喉**：彰化站北方咽喉由山線與海線共用，兩線進路不得同時開放。
- **端末站與分歧站的相鄰修正**（`remove_station_links`／`add_station_links`）：
  站序是「印在同一張表上的順序」，端末支線會被排進主線的站序中間，或是共用
  一份時刻表的分歧站互相干擾，讓匯入漏掉或誤生相鄰關係。已知兩個例子：
  - **六家－上員**（誤生的相鄰關係）：內灣線與六家線共用一份時刻表，站序把
    六家排在竹中與上員之間，於是產生一條不存在的「六家－上員」相鄰關係，讓
    所有內灣線班次繞經六家。實際上六家是竹中分歧出去的端末站，內灣線由竹中
    直接接上員，因此刪掉前者、補上後者。
  - **瑞芳－四腳亭**（漏掉的相鄰關係）：兩者是宜蘭線本線相鄰站，但 `_build_edges`
    完全沒有產生它們的直接連線，只剩深澳線分歧（瑞芳→海科館→八斗子→四腳亭）
    可通。最可能的原因是「平溪深澳線」時刻表某處把兩條支線的站名列在同一張
    表／同一列裡（平溪線與深澳線都在瑞芳分歧，公開時刻表常合併呈現），讓
    `_prune_spanned` 誤判瑞芳與四腳亭之間「其實還有別站」而刪掉這條候選連線。
    這類跨表格干擾難以在 `_prune_spanned` 裡一般化處理，因此直接用
    `add_station_links` 補回。

  兩者補上的區間長度都由該兩站的最短排點時間推估。

匯入後這些規則會由 `validate_route()` 逐條驗證，任何違反都會讓匯入回報
失敗，資料不會悄悄變壞。

## 已知的來源限制

- **南迴線沒有區間車時刻表**，站序只能取自對號列車表；該表在枋寮以南列出
  全部車站，因此這一段可安全採用（設定在 `adjacency_from_column_layout`）。
- 對號列車時刻表中，主要車站的「到達／開車」分列兩行，本專案只取到達時刻。
- 行駛日期符號（▲△⊕◆…）已保留在 `operating_mark`，但**尚未實作按日期
  篩選班次**，所有班次一律視為每日行駛。
