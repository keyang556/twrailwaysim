# twrailwaysim — 臺灣鐵路人員模擬器

臺灣鐵路運轉主題的**無障礙優先**人員模擬遊戲。純鍵盤操作，所有狀態變化都有文字回饋。

目前完成範圍：**第一階段司機員模式（里程碑 M0–M3，另含 M4／M5 的部分基礎）**。
其餘角色與系統尚未實作，詳見〈完成度〉一節。

依據文件：

- [DEVELOPMENT_SPEC.md](DEVELOPMENT_SPEC.md) — 開發規格 0.1
- [docs/chat_decisions.md](docs/chat_decisions.md) — 對話中已確認的路線與鍵位結論

**兩份文件衝突時，以 chat.md 的結論為準。**

---

## 快速開始

需要 Python 3.13 以上（開發環境為 3.14）。

```bash
python -m pip install -e ".[dev,gui]"
```

啟動遊戲（主控台介面，預設）：

```bash
python -m railway_sim
```

只做資料與鍵位檢查，不啟動遊戲：

```bash
python -m railway_sim --check
```

列出可用情境：

```bash
python -m railway_sim --list-scenarios
```

列出可駕駛的車次（可加關鍵字過濾車次、車種、車輛型式、起訖站或沿途車站）：

```bash
python -m railway_sim --list-services 集集
```

執行測試：

```bash
python -m pytest
```

### 情境

情境使用的都是 **115 年 7 月 1 日實施時刻表**中的實際車次。

| 代碼 | 內容 |
|---|---|
| `local` | 區間車 2115 次，豐原往彰化各站停車（含成功站停靠） |
| `express` | 區間快 2021 次，與 2115 次同路線但**通過**成功站 |
| `tze_chiang` | 自強號 101 次，臺中往潮州，通過成功站（§25.7） |
| `chengzhui` | 區間車 2600 次，臺中經**成追線**往大甲，不經彰化（§10.4） |
| `red_signal` | 區間車 2115 次＋前方列車故障，須在停止號誌前停車 |

```bash
python -m railway_sim --scenario chengzhui
```

全部 953 個車次都可以直接指定，不限於上列情境：

```bash
python -m railway_sim --service 1801
```

視窗介面沒有命令列可用，因此改由**開場的車次選擇視窗**提供同樣的能力
（見下一節）。

## 介面選擇

專案提供兩種介面，**運轉邏輯與可做的事完全相同**，介面只負責送入按鍵與輸出文字。
行前提要、列車狀態與所有播報文字都來自 `DriverSession`，沒有任何一邊自己組字串
（§25.5：必要資訊不得只存在於單一介面）。`tests/test_wx_app.py` 會比對兩邊註冊的
動作集合完全一致。

### 主控台（預設，`--ui console`）

規格 §26 指定的終端遊戲。**這是目前唯一可保證螢幕閱讀器行為的介面**：畫面只在有事件時輸出新的一行純文字，NVDA 會自動朗讀主控台的新增內容，且不會因持續重繪造成語音塞車。

### wxPython（`--ui wx`）

規格 §5.1 建議的 GUI。版面為兩個唯讀多行文字欄位（運轉播報、列車狀態），可用方向鍵逐行閱讀；按鍵以 `EVT_CHAR_HOOK` 在視窗層級攔截，焦點在哪個欄位都能操作。

```bash
python -m railway_sim --ui wx
```

沒有指定 `--service` 或 `--scenario` 時（安裝版直接執行就是這種情形），會先開啟
**車次選擇視窗**：上方是搜尋欄，可用車次、車種、車輛型式、起訖站或沿途車站過濾；
下方是清單，上下鍵選擇、Enter 開始。遊戲中按 `Esc` → 「選擇其他車次」可以隨時換車，
不必重開程式。

暫停選單的項目與主控台一致（繼續運轉／快捷鍵說明／列車狀態／離開遊戲），另多一項
「選擇其他車次」。未綁定的按鍵一樣會回覆說明（§7.2）。

模擬時間依 `time.perf_counter()` 的**實際經過時間**推進，不是照計時器間隔猜；
開啟說明或暫停選單時暫停推進，恢復時重設計時基準，因此不會在恢復的瞬間把列車
往前補推一大段。

> **關於語音**：若系統上存在 NVDA 官方的 `nvdaControllerClient64.dll` 且 NVDA 正在執行，播報會直接送給 NVDA 朗讀。本專案不散布該 DLL，**此路徑未在開發環境中實測**。沒有它時所有資訊仍以純文字完整呈現，遊戲功能不受影響。

## 快捷鍵

**功能相同者，鍵位一律與 OpenBVE 相同**，以便在兩者之間切換時不必重新適應。
對照來源為 OpenBVE 的 `assets/Controls/Default.controls`，修飾鍵位元
Shift=1、Ctrl=2、Alt=4（`OpenBveApi/Interface/Input/KeyboardModifier.cs`）。

鍵位由 [`data/keymap.json`](data/keymap.json) 載入，可直接修改，程式不硬編碼按鍵。安裝版要自訂鍵位時，請複製整個 `data` 資料夾並透過 `--data-dir` 或 `RAILWAY_SIM_DATA_DIR` 指定它。
遊戲中按 **F1** 隨時查詢。

### 駕駛操作

| 按鍵 | 功能 | OpenBVE 指令 |
|---|---|---|
| `Z` | 增加電門段位（0–5） | `POWER_INCREASE` |
| `A`、`,` | 回到惰行或降低控制段位 | `POWER_DECREASE`、`BRAKE_DECREASE` |
| `.` | 增加常用制軔段位（0–7） | `BRAKE_INCREASE` |
| `/` | 緊急制軔 | `BRAKE_EMERGENCY` |
| `Enter` | 鳴笛 | `HORN_PRIMARY` |
| `R` | 鬆軔 | 無對應 |
| `E` | 解除緊急制軔（須列車停妥） | 無對應 |

本專案的減段是單一動作（降低目前作用中的控制），對應 OpenBVE 分開的兩個
緩解指令，因此 `A` 與 `,` 都叫到它。

### 狀態查詢

OpenBVE 的無障礙指令使用 `Shift+Ctrl+字母`，本專案沿用；括號內為單鍵別名。

| 按鍵 | 功能 | OpenBVE 指令 |
|---|---|---|
| `Ctrl+Shift+S`（`V`） | 播報目前速度與允許速度 | `ACCESSIBILITY_CURRENT_SPEED` |
| `Ctrl+Shift+A`（`G`） | 播報前方號誌 | `ACCESSIBILITY_NEXT_SIGNAL` |
| `Ctrl+Shift+T`（`N`） | 播報下一站與停靠別 | `ACCESSIBILITY_NEXT_STATION` |
| `P` | 播報目前位置 | 無對應 |
| `T` | 播報列車狀態 | 無對應 |

> **主控台的限制**：終端機只收得到控制字元，無法區分 `Ctrl+S` 與
> `Ctrl+Shift+S`。主控台把控制字元一律視為 `Ctrl+Shift+字母`；由於本專案沒有
> 使用單獨的 `Ctrl+字母`，在本鍵位表內不會產生歧義。單鍵別名在任何介面都能用，
> wx 介面則收得到真正的修飾鍵狀態。

### 系統

| 按鍵 | 功能 | OpenBVE 指令 |
|---|---|---|
| `F1` | 快捷鍵說明 | 無對應 |
| `F2` | 重複播報最近一則訊息 | 無對應 |
| `Esc` | 暫停選單（含離開遊戲） | `MENU_ACTIVATE` |

### 與先前配置的關係

先前依 chat.md 訂下的是「`D` 電門、`A` 制軔、`Space` 緊急制軔」。改採 OpenBVE
鍵位後 `A` 由制軔改為減段，兩者確實衝突；依「相同功能需與 OpenBVE 相同」的
指示以 OpenBVE 為準。舊配置完整保留在 profile `driver_legacy`：

```bash
python -m railway_sim --keymap-profile driver_legacy
```

`keymap.json` 中每個鍵位都以 `source` 欄位記錄依據（沿用 OpenBVE 的哪一條，
或是規格的哪一節）。衝突檢查由 `Keymap.conflicts()` 執行，`tests/test_keymap.py`
強制其為空並逐條比對 OpenBVE 的鍵位，啟動時也會再檢查一次。

## 成功／追分／彰化路線模型

這是規格 §10 與 chat.md 反覆修正的部分，也是本專案最嚴格保護的規則。

模型依 chat.md「海線倒插在成功南、彰化北」建立：成追線在**成功站南方、彰化以北**的分歧 `JCT_CHENGZHUI` 朝成功方向倒插接入山線。

```text
              臺中
               │（山線）
              成功
               │
        JCT_CHENGZHUI ─── 追分 ─── 海線
               │              │
               │              │（海線）
        JCT_CHANGHUA_N ───────┘
               │
              彰化
```

因為聯絡線朝北接入，**由追分進入該分歧後只能往成功，不能直接轉向彰化**。這個限制無法用「有連線就能通行」表達，因此在分歧節點上以 `allowed_transitions` 明確列出可行轉向。四條規則於是成為拓撲本身的性質：

| 情境 | 正確路徑 | 禁止 |
|---|---|---|
| 海線往彰化 | 追分 → 彰化 | 經成功（§10.2、§25.8） |
| 海線往臺中 | 追分 → 成功方向 → 臺中 | 經彰化（§10.3、§25.9） |
| 臺中／豐原往海線 | 成功 → 追分 → 海線 | 經彰化（§10.4） |
| 彰化往海線 | 彰化 → 追分 | 經成功 |
| 山線列車 | 彰化 ↔ 成功 ↔ 臺中 | 經追分（chat.md 五） |

防線有兩層，`tests/test_route_rules.py` 兩層都測：

1. **拓撲層**：錯誤路徑在 `Route.build()` 就會擲出例外。
2. **規則層**：即使繞路繞得出來，`validate_route()` 也會攔下。

實際時刻表匯入後，這些規則不再只由測試資料驗證，而是由 **953 個真實班次**
驗證：其中 28 班以車次後綴「追」標示經由成追線，全部走 臺中 → 成功 → 追分 → 海線
且**沒有任何一班經過彰化**。

### 成功站停靠規則

先前依 chat.md「成功站資料修正」推定，**現已由 115 年 7 月 1 日實施的實際
時刻表確認**：

| 車種 | 實際時刻表 | 先前推定 |
|---|---|---|
| 區間車 | **停靠** | 停靠 ✓ |
| 區間快 | **一律通過**（無任何一班停靠） | 「依班次設定，一般通過」 |
| 自強號（含普悠瑪、太魯閣、自強3000） | **一律通過**（§25.7）| 一律通過 ✓ |
| 莒光號 | 不行經成功站 | 「預設通過，待正式時刻表確認」 |

`stop_rules` 現在由時刻表中實際辦客的班次統計而得，不再是人工推測；
但它只表示「該車種在本站至少有一班列車停靠」。某一班次停或不停，一律以
**該班次的停靠表**判斷，絕不由「列車行駛於這條路線」推論（§9.1）。
把自強號設成成功站停靠站的班次資料會被 `validate_service()` 擋下並使啟動失敗。

> **先前一項待確認的建模判斷，已由實際資料確認**
>
> chat.md 中的示意圖把山線寫成「彰化 ─ 大慶 ─ 臺中」而省略成功，與規格 §10.1
> 「成功是山線車站」不一致；當時採用規格的寫法。
>
> 實際時刻表證實規格是對的：**成功是山線車站，山線列車會經過成功**（停或不停
> 看班次），共有 66 班對號列車與 14 班區間快行經但不停靠。山線南下實際順序為
> 臺中 → 五權 → 大慶 → 烏日 → 新烏日 → 成功 → 彰化。

## 時刻表資料

遊戲資料由**臺鐵公布的 `.ods` 時刻表**匯入產生，目前為
**115 年 7 月 1 日（2026-07-01）實施**版本：全臺 **240 站、953 個車次、307 條路線**。

改點時不需要手動編輯 JSON，把新檔案放進一個資料夾再跑一個指令即可：

```bash
python -m railway_sim.dataset --source <時刻表資料夾>
```

完整流程、資料可信度與少數需人工維護的部分，見
[docs/timetable-import.md](docs/timetable-import.md)。

### 車種與車輛型式

**車種（`service_class`）決定停靠規則，車輛型式（`train_type`）決定運轉性能，兩者分開。**
「自強號」是車種不是車輛型式：時刻表的車種欄把 EMU3000 印成「自強3000」、普悠瑪與
太魯閣各自成一欄，其餘印「自強」，實際上是四種完全不同的車輛。

| 時刻表車種 | 車輛型式 | 營運速度 | 常用／緊急減速度 | 班次數 |
|---|---|---|---|---|
| 自強3000 | EMU3000 型電聯車（12 輛 6M6T） | 130 | 3.6／4.32 km/h/s | 80 |
| 自強 | 推拉式自強號（2M12T） | 130 | 3.6／5.5 km/h/s | 39 |
| 自強（人工確認 4 班） | DR3100 型柴聯車（3 輛） | 110 | 3.0／3.0 km/h/s | 4 |
| 普悠瑪 | TEMU2000 型電聯車（8 輛 4M4T） | 130 | 3.6／4.32 km/h/s | 32 |
| 太魯閣 | TEMU1000 型電聯車（8 輛 4M4T） | 130 | 3.6／4.32 km/h/s | 6 |
| 區間車／區間快（電氣化區間） | EMU900 型電聯車（10 輛 5M5T） | 130 | 無來源，暫用同期電聯車數值 | 682 |
| 區間車／區間快（非電氣化支線） | DR1000 型柴油客車（3 輛） | 110 | 2.448／2.448 km/h/s | 103 |
| 莒光 | 莒光號（電力機車牽引客車） | 110 | 無來源，全部為測試值 | 7 |

另外收錄 **DR3100 型柴聯車**（柴聯自強號，營運速度 110、減速度 3.0 km/h/s）。它 2023 年
4 月 26 日改點後退出西部幹線與宜蘭線，僅保留於東部幹線；115 年 7 月 1 日的時刻表無法
從車種欄分辨哪些「自強」由它擔當（與推拉式自強號共用同一個車種名稱），因此改為人工
確認車次 209、221、238、246（樹林－花蓮、蘇澳新－樹林、南澳－樹林）由它擔當，逐車次
覆寫（見下方「非電氣化支線一律是 DR1000」小節）；DR1000 的牽引性能則由這份來源推算
而來。

#### 非電氣化支線一律是 DR1000

只要班次的停靠或通過表碰到下列任何一站，車輛型式就是 DR1000——即使它有一大段行程
跑在電氣化幹線上（例如彰化直通車埕的集集線區間快）：

| 支線 | 車站 |
|---|---|
| 集集線 | 源泉、濁水、龍泉、集集、水里、車埕 |
| 內灣線（竹中至內灣） | 上員、榮華、竹東、橫山、九讚頭、合興、富貴、內灣 |
| 平溪線 | 大華、十分、望古、嶺腳、平溪、菁桐 |
| 深澳線 | 海科館、八斗子 |

清單只列**支線本身**的車站。二水、三貂嶺、瑞芳都在幹線上，停靠它們的幹線列車不受
影響。**六家線（竹中至六家）已電氣化**，新竹至六家的 82 班區間車維持 EMU900。

判斷用的車站集合來自**完整的行經路徑**（尋路算出的每一個節點），不是只看時刻表印
出時刻的停靠站——對號列車時刻表只印主要車站，實際尋路可能補入時刻表沒印出來的
中間站，這些站一樣是列車真的會經過的地方。

車次 209、221、238、246（自強號，樹林－花蓮／蘇澳新－樹林／南澳－樹林）另外人工
確認由 **DR3100 型柴聯車**擔當，優先於車種與支線判斷——時刻表的車種欄無法分辨
「自強」底下同時有推拉式自強號與 DR3100 兩種車輛。

#### 路網缺一條邊會誤判成柴油客車：瑞芳－四腳亭

車輛型式判斷改用完整路徑後，揭露了一個**先於本次車輛資料修正就存在**的路網缺陷：
`routes.json` 完全沒有瑞芳與四腳亭這兩個宜蘭線本線相鄰站的直接連線。深澳線在瑞芳
分歧（見下方説明），是圖裡唯一連得到四腳亭的路徑，於是任何需要經過此處的路線都被
迫繞經深澳線車站（瑞芳→海科館→八斗子→四腳亭）——連只有兩站、時刻表明確排點
6 分鐘直達的區間車都不例外，證明問題出在路網本身缺一條邊，不是任何特定車次的
判斷邏輯。這連帶讓 157 個東部幹線班次（太魯閣、普悠瑪、自強3000 等）的路徑也
「經過」深澳線車站；若只是照車輛型式判斷的新規則把它們一律改成 DR1000，會產生
另一個同樣錯誤的結果——這些真的是電聯車，不會跑深澳線。正確做法是修路網本身：
在 `topology_overrides.json` 的 `add_station_links` 補上瑞芳－四腳亭的直接連線
（`remove_station_links`／`add_station_links` 用法見上一節六家的例子），而不是
將錯就錯地改車輛型式。

### 資料來源政策

嚴格遵守規格 §22 與 §27。每個資料檔的 `meta.data_policy` 都註明來源與狀態，
`meta.provenance` 則記錄實施日期與每個來源檔案的 SHA-256：

| 資料 | 狀態 |
|---|---|
| 站名、站序、車次、車種、停靠站、通過站、時刻 | `official` — 取自臺鐵公布的時刻表 |
| 車站的車種停靠規則（`stop_rules`） | 由時刻表中實際辦客的班次統計而得，屬推導結果 |
| 區間長度（`length_m`） | `estimated_from_timetable` — 由排點時間推估，**不是實際里程** |
| 車輛的最高速度、編組長度、起動加速度、減速度 | 取自各車型的公開技術諸元，逐欄以 `field_status` 標示 `official`／`derived_from_source`／`test_data` |
| 行駛阻力係數（`resistance_ms2`） | `test_data` — 無公開來源，改用通用的戴維斯式係數，並以「每一車型都達得到來源標示的營運速度」為校驗條件 |
| 區間速限 | `test_data` — **明確標示的測試資料，非臺鐵實際數值** |
| 月台數、股道配置、月台長度 | `null` + `unknown` — 無可靠公開來源，未推測 |

停車範圍（±50 公尺）、注意號誌速度（60 km/h）等亦為測試值，因為真實月台長度與號誌位置無公開來源。

`trains.json` 的 `meta.known_source_conflict` 記錄了一項來源本身的矛盾：DR3100 型的
技術諸元同時標示「起動加速度 0.5 km/h/s」與「營運速度 110 公里」，但 0.5 km/h/s
（0.139 m/s²）在 110 公里時產生的牽引力小於同速度下的行駛阻力，列車根本到不了 110。
因此 DR1000 與 DR3100 的起動加速度改由同一份來源的引擎出力與編組重量推算，
標記 `derived_from_source`。

### 已知限制

- 區間長度由排點時間推估、速限為測試資料，運轉時間不等於實際運行時間。
- 對號列車時刻表中主要車站的「到達／開車」分列兩行，本專案只取到達時刻。
- 號誌只有三顯示，沒有臺鐵實際的號誌種類與現示。
- 進站／出發號誌未與月台股道連動（缺月台資料）。
- ATP 不強制營業停靠：規格 §14.1 把「前方停車點距離」列為監控內容，本專案將其實作為**提醒**而非強制介入，因為營業停靠不是保安功能——停不下來屬於司機的行車違規（應停未停，§9.2），而非 ATP 應接管的情況。強制介入僅限區間速限、號誌與冒進號誌。
- wx 介面的 NVDA 直接語音路徑未實測（見上）。
- 時刻表的車種欄無法分辨同一車種底下的不同車輛（例如哪些「自強」由 DR3100 柴聯車擔當），因此車輛型式是依車種名稱與線別電氣化與否分派，不是逐車次的實際運用。
